# Release 1.2.5 — Baluarte Launcher com artefatos baixáveis

**Status:** `PREPARED — PENDING MAIN VALIDATION AND DESKTOP RELEASE`

**Versão do site:** `1.2.5`

**Versão do Launcher:** `1.2.5`

**Tag planejada do desktop:** `desktop-v1.2.5`

**Branch oficial:** `main`

**Autor:** Manus AI

## Resumo

A release `1.2.5` existe para resolver a experiência de distribuição do Baluarte Launcher. O objetivo é que uma pessoa consiga abrir a página [`/baixar`](https://projeto-baluarte.vercel.app/#/baixar), selecionar o sistema operacional e receber um asset real de uma release pública do GitHub, em vez de encontrar somente código-fonte, uma versão sem instalador ou uma cadeia de atualização com números divergentes.

Esta release não declara a V2 estável, não ativa cobrança real, não aplica DDL remoto e não altera a política de Auth/RLS. Ela alinha a versão web e desktop e fortalece o workflow que constrói os binários nativos.

## Diagnóstico da inconsistência anterior

A auditoria encontrou três fatos relevantes:

| Área | Estado auditado | Consequência |
|---|---|---|
| Site | `package.json` e `src/data/version.js` em `1.2.0` | A web informava uma linha diferente do Launcher |
| Launcher | `desktop/package.json` em `1.1.5` | O instalador e o auto-update anunciavam uma linha antiga |
| Publicação | Workflow acionado por `desktop-v*`; a release `v1.1.0` possui assets, mas é uma trilha separada | O tag web não garante assets desktop e o usuário pode não encontrar o download correto |

A página `/baixar` consulta `https://api.github.com/repos/Lucas-Belucci-Bellini/Projeto-Baluarte/releases/latest`. Portanto, a experiência pública depende de uma release GitHub não-draft, não-prerelease e com assets que correspondam às extensões e plataformas esperadas.

## Alterações da 1.2.5

A versão é sincronizada em `package.json`, `package-lock.json`, `desktop/package.json`, `desktop/package-lock.json`, `src/data/version.js` e `public/sw.js`. O Service Worker passa a usar `baluarte-v1.2.5`, fazendo o navegador instalar a versão nova e limpar caches anteriores conforme o teste `test/versao.test.js`.

O texto do auto-update do Launcher deixa de anunciar `1.1.5` e passa a anunciar `1.2.5`. O comportamento de segurança permanece: `autoDownload = false`, pergunta explícita antes do download e confirmação antes da instalação.

O workflow `.github/workflows/desktop-release.yml` passa a usar `1.2.5` como default manual e valida, antes do `electron-builder`, que `desktop/package.json` corresponde ao tag `desktop-v1.2.5` quando o workflow é disparado por tag. Isso evita produzir assets com nome de versão diferente da release.

## Artefatos esperados

A matriz do workflow constrói o binário nativo em cada sistema operacional e executa `electron-builder --publish always`. A release pública deverá conter, no mínimo:

| Plataforma | Asset esperado | Manifesto de atualização |
|---|---|---|
| Windows | `Baluarte-Launcher-Setup-1.2.5.exe` | `latest.yml` |
| Linux | `Baluarte-Launcher-1.2.5.AppImage` | `latest-linux.yml` |
| macOS | `Baluarte-Launcher-1.2.5-arm64.dmg` ou o `.dmg` produzido pela matriz macOS | `latest-mac.yml` |

Os nomes finais, tamanhos, SHA-256 e URLs não devem ser presumidos. Eles serão registrados somente após `gh release view v1.2.5` ou após a consulta da release associada ao tag `desktop-v1.2.5`.

## Critérios de aceite

A release só será marcada como publicada quando o commit no `main` estiver validado e os seguintes critérios forem verdadeiros:

1. `test/versao.test.js` confirma a igualdade entre site, Service Worker e `src/data/version.js`.
2. `npm run tipos:ts`, `npm run tipos:v2`, `npm test`, `npm run build`, `npm run v2:integracao`, `npm run smoke` e `npm run caminho-critico` passam.
3. O runtime Rust local é classificado honestamente se Cargo 1.75.0 continuar incapaz de interpretar `edition2024`; o workflow remoto continua sendo a evidência do build nativo.
4. O workflow Desktop Release passa em Windows, macOS e Ubuntu.
5. A release pública tem os três instaladores e os três manifestos, sem ficar em draft ou prerelease.
6. A API de releases retorna a release esperada em `/releases/latest`.
7. Cada asset tem tamanho maior que zero, URL pública e nome correspondente à plataforma.
8. A página `/baixar` consegue escolher o asset da plataforma detectada e mantém fallback para a página de releases quando a API está offline ou limitada.
9. O relatório final registra o SHA do commit, tag, workflow, run IDs, assets, tamanhos, downloads observados e URLs.

## Rollback

O rollback do código é o commit anterior à promoção da `1.2.5`. O rollback da distribuição consiste em não publicar, ou remover a tag desktop somente se a publicação estiver incorreta e houver confirmação operacional. Não se deve apagar uma release pública válida para esconder falha de documentação.

Se os assets estiverem ausentes ou incorretos, a release deve ser classificada como `BLOCKED — ARTIFACTS`, o workflow deve ser corrigido em novo commit e a tag não deve ser reutilizada com force push. A correção deve usar uma nova tag de manutenção ou uma release substituta documentada, preservando o histórico.

## Segurança e limitações

Os instaladores não são assinados nem notarizados nesta etapa, conforme a documentação existente do Launcher. Windows SmartScreen e Gatekeeper podem emitir avisos. O usuário deve baixar somente a partir da release oficial do repositório e verificar a URL, o nome e o tamanho do asset.

A publicação não aplica migrations Supabase, não ativa Auth/RLS remoto, não habilita providers externos e não torna o Runtime Rust localmente compilável com Cargo 1.75.0. A construção nativa no GitHub Actions usa a toolchain definida pelo workflow e deve ser validada por run.
