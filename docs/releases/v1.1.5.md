# Projeto-Baluarte 1.1.5

## Status

`RELEASE CANDIDATE — aguardando todos os workflows do SHA final`

## Resumo

A versão 1.1.5 consolida uma onda incremental da V2 sobre a V1 funcional. O foco desta versão é segurança de sessão, isolamento de dados, fundação de Billing, presença musical do JARVIS, observabilidade do Module Registry e uma superfície visual mais informativa para o dashboard do JARVIS.

> Esta release não declara a V2 concluída e não ativa Supabase staging, providers financeiros reais, OpenClaw ou envio de mensagens externas.

## Funcionalidades

| Área | Entrega |
|---|---|
| TypeScript | Páginas migradas para implementação canônica TypeScript com wrappers JavaScript de compatibilidade |
| Auth | Login, cadastro, Google OAuth, refresh, logout e rejeição de sessões incompletas |
| OAuth | Limpeza de tokens do fragmento, rejeição de token parcial e redirect restrito à origem/path atual |
| Ownership | JWT encaminhado como Bearer pelo Data Layer e contratos locais para isolamento por `auth.uid()` |
| RLS | Matriz tipada de staging com cenários anônimo, dono, não dono, operador e usuário comum |
| Billing | Transações locais atômicas, idempotência, observabilidade e drivers HTTP server-side de leitura/escrita |
| JARVIS | Presença musical passiva, Spotify OAuth PKCE em memória e reação visual sutil do núcleo 3D |
| Registry | Health por módulo, degradação isolada, restart limitado e quarentena após falhas excedentes |
| Maintenance | `maintenance`/`disabled` exigem autorização server-side e motivo auditável; ausência de autorização nega por padrão |
| Vigia | Navegação smoke com `DOMContentLoaded` e timeout configurável por rota |

## Estética e experiência

O dashboard do JARVIS recebeu uma organização visual em grid responsivo com painéis de sessões, memórias, eventos, commits e atividade agregada. Os estados online, demo, warning, erro e offline são visualmente distintos, e a atividade de commits usa barras agregadas por dia para reduzir ruído. O núcleo 3D do JARVIS reage de forma sutil quando existe contexto musical, sem transformar música ou Spotify em dependência obrigatória do boot da V1.

## Segurança e limites

A autorização efetiva continua server-side/RLS. Claims decodificados no cliente não são autoridade administrativa, service role não é enviado ao frontend e o fallback do Registry não ativa módulo desconhecido. A validação remota de RLS depende de um projeto Supabase staging aprovado, fixtures isoladas, cleanup idempotente e credenciais protegidas.

## Validação esperada

A release só deve ser marcada como estável após `npm run tipos:ts`, `npm run tipos:v2`, `npm test`, `npm run build`, `npm run v2:integracao`, `npm run smoke`, `npm run caminho-critico` e os workflows remotos aplicáveis concluírem com sucesso no SHA da release.

## Rollback

O rollback da versão é o revert do commit de versionamento e a remoção da tag/release `v1.1.5` se algum gate remoto revelar regressão. As funcionalidades V2 são isoláveis e podem permanecer `degraded`, `maintenance`, `disabled` ou `quarantined` sem derrubar Core, Router, Home ou a V1.
